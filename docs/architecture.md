# 架构与兼容策略

## 系统边界

```text
浏览器
  │ HTTPS / HTTP
  ▼
kdae-panel
  ├── 认证与会话：SQLite + Argon2id
  ├── 配置事务：临时文件、validate、备份、原子替换、回滚
  ├── dae 适配：固定参数调用公开 CLI
  ├── 服务管理：systemctl（procd 部署下是 ubus + init 脚本，见「服务后端」）
  ├── 日志读取：journalctl JSON（procd 部署下是 logread，见「服务后端」）
  ├── 网络探测：对节点服务器发起 TCP 握手
  └── 定时重载：按间隔触发 dae reload 以刷新订阅
        │
        ▼
      dae.service（procd 部署下是 /etc/init.d/dae）
```

面板和 dae 是独立进程。面板不链接 dae 的内部包，不要求修改 dae，也不需要向上游增加 Unix Socket API。

## 稳定契约

面板只依赖以下外部契约：

| 契约 | 用途 | 变化风险 |
|---|---|---|
| `dae --version` | 显示安装版本 | 低 |
| `dae --help` | 基于能力而非版本号启用功能 | 低 |
| `dae export outline` | 动态配置结构 | 低 |
| `dae validate -c` | 使用当前二进制校验候选配置 | 低 |
| `dae reload` | 应用配置 | 低 |
| `.dae` 入口配置 | 配置的唯一真实来源 | 中 |
| systemd 单元 / procd init 脚本 | 生命周期与资源状态 | 低 |
| journald JSON / logread | 近期日志 | 低 |

默认启用的 dae 版本管理还会依赖四个外部契约，它们不属于 dae 本身，风险也更高：GitHub Release 的 `dae-linux-<平台>.zip` 与 `.dgst` 命名（中）、GitHub Actions 接口的 `digest` 字段（中）、`nightly.link` 的重定向服务（高，第三方），以及首次安装依赖的发布包内容——`dae.service` 里的默认路径 `/usr/bin/dae` 与 `/etc/dae/config.dae`，面板靠替换这两个字面量把单元改写到实际路径（中，仅 systemd 部署；procd 部署下这份服务定义由 `kdae-panel` 软件包提供，面板不写它，详见下方「服务后端」）。

不稳定的内部对象、eBPF Map、Go 包、内存布局和普通日志文本均不作为控制契约。

## 服务后端

面板对"如何控制 dae 这个系统服务"的全部认知收在 `internal/host` 包里，对上层只暴露一个
`Manager` 接口（`Status`、`Action`、`RestartSelf`、`Logs`、`Interfaces`），具体由哪套 init 系统
实现由本包决定，其余代码不区分。

两套实现分工不同：

- **systemd**（`internal/host/systemd.go`）：`Status` 用 `systemctl show` 解析生命周期、资源与
  重启计数；`Logs` 用 `journalctl --output json` 取结构化日志。
- **procd**（`internal/host/procd.go`）：`Status` 用 `ubus call service list` 取运行状态与命令行，
  用 `<init 脚本> enabled` 的退出码判断开机自启，用 `/proc/<pid>/{status,stat,environ}` 补内存、
  线程数与环境变量；`Logs` 用 `logread -e <name>`，并需要把两种 `logread` 时间戳格式
  （ubox 带年份、busybox 不带）都解析成本地时间再转 UTC。procd 不暴露重启计数器，`Status` 里的
  `Restarts` 字段刻意留空（`omitempty`，不填 0——填 0 会被上层的崩溃循环检测误读成"确实没重启
  过"），前端相应地显示"—"而不是"0"。

两处两套后端必须给出同一种答案，否则同一台机器换个部署方式界面就变样：

- `StartedAt` 一律是 RFC 3339。systemd 把 `ExecMainStartTimestamp` 那种本地化写法
  （`Mon 2026-08-01 10:00:00 CST`）归一过来，procd 则用 `/proc/<pid>/stat` 的 starttime 配
  `/proc/uptime` 算出已运行时长，再由当前时刻回推。procd 侧不直接换算 starttime 的绝对时刻——
  那要引 `/proc/stat` 的 btime，而路由器开机后常被 NTP 校时一次，算出来的时刻可能落在未来。
- 日志级别名共用 `internal/host/loglevel.go` 的一张表。dae 写的是 logrus 那套（`warn`、`fatal`、
  `trace`），syslog 前缀写的是另一套（`warning`、`crit`），日志页按 `level` 精确匹配做筛选，
  两边不归一到同一组名字就会出现"同一条日志在 systemd 上筛得出、在 procd 上筛不出"。

服务控制的 `enable-now` / `disable-now` 两个动作在两套后端上落法不同：systemd 直接用
`systemctl enable --now`，rc.common 没有 `--now`，procd 拆成 `enable` + `start` 两条命令按同样的
顺序执行，任一步失败都不掩盖——面板会照返回值告诉用户"已启动，并已设为随系统启动"。

后端的选择由 `host.Backend`（`auto` / `systemd` / `procd`）决定：`auto` 探测 `/sbin/procd` 是否
存在，存在即判为 procd，否则 systemd；可用 `--service-backend` 命令行参数或
`KDAE_PANEL_SERVICE_BACKEND` 环境变量显式覆盖探测结果。选中的后端会记入启动日志（`已选定服务
后端`），并由 `GET /api/v1/health` 响应的 `backend` 字段实时暴露，方便在不方便看日志的环境里
确认当前实际生效的是哪一套。

`daeinstall` 包（dae 版本管理）同样要面对"服务定义"这件事在两套 init 系统上含义不同，抽出了
`unitProvisioner` 接口封装差异：

- **systemd 下**，服务定义（`dae.service`）由面板从发布包渲染并写入 `/etc/systemd/system`，
  首次安装时创建，卸载 dae 时删除——它的生命周期与某一次具体的安装/卸载事务绑定。
- **procd 下**，服务定义（`/etc/init.d/dae`）是 `kdae-panel` 软件包自带的文件，不属于任何一次
  dae 安装。面板只校验它是否存在、是否是普通文件，从不改写、从不删除；卸载 dae 时也不会动它，
  这样用户之后仍可以从面板重新安装 dae，而不必重装整个软件包。

两套实现都满足同一个 `unitProvisioner` 接口（`Path`、`WritableDirs`、`RemovablePaths`、
`VerifyRemovable`、`Detect`、`Plan`、`Commit`），`daeinstall.Installer` 的安装、卸载事务逻辑不
区分后端，只在构造时按 `host.Backend.Resolve()` 的结果选择其中一个实现。

故障诊断（`internal/diagnostics`）是第三处必须分后端的地方，但分的只有措辞。检查项、判定条件、
`level` 与汇总计数两套后端逐字相同，`internal/diagnostics/wording_test.go` 用同一组输入跑两遍并
逐项比对 ID、分类与级别，防止有人顺手把"结论"也改成分支。分叉的是证据标签与修复建议，收在
`internal/diagnostics/wording.go` 的一张表里：systemd 说 `systemctl status dae`、journald、
`dae.service` 和单元的 `ReadWritePaths`，procd 说 `ubus call service list`、`logread`、
`/etc/init.d/dae`；缺 BTF 时 systemd 说换内核，procd 说那是固件的编译期开关
（`CONFIG_KERNEL_DEBUG_INFO_BTF`），装软件包补不出来。别处文案说错了顶多让人多看一眼，诊断页
说错了是把一个已经卡在故障里的人直接支到不存在的文件和命令上，而会点开这一页的正是最没有余力
分辨的那批用户。后端未知时退回 systemd 措辞——那是上游的原生部署，宁可对 procd 用户少说一句，
也不要对 systemd 用户改口。

## 配置事务

保存操作在进程级互斥锁内串行执行：

```text
检查客户端提交的旧 SHA-256
  → 在入口配置同目录写入候选 .dae 文件
  → 继承入口文件权限
  → fsync 候选文件
  → dae validate -c 候选文件
  → 清理超出 50 份或 256 MiB 的旧备份
  → 将旧配置写入 0600 备份文件并 fsync 父目录
  → 同文件系统原子替换入口文件并 fsync 父目录
  → 运行中则 dae reload <服务后端记录的 PID>，未运行则延后到下次启动
  → 失败时恢复旧磁盘配置
```

候选文件与入口配置位于同一目录，确保 dae 的相对 `include` 路径仍按入口目录解析。已有配置必须携带 SHA-256 乐观锁，用于阻止两个浏览器或外部编辑器互相覆盖。备份最多保留 50 份且总量不超过 256 MiB。配置保存、手动重载和订阅刷新共用同一个查服务状态的控制器：运行中显式传服务后端记录的 PID（systemd 的 `MainPID`、procd 的实例 PID），不依赖可能缺失的 `/var/run/dae.pid`；未运行时保留新配置并明确提示下次启动生效，其他重载错误仍回滚。

配置历史同时承载保存前自动备份和用户主动保存的存档。主动保存的内容仍使用同一类权限为 `0600` 的 `.dae` 文件，名称和备注单独写入同编号的 `.meta.json` 文件，避免改变旧版面板的恢复格式。恢复存档继续走完整的校验、乐观锁、自动备份、原子替换、重载和失败回滚流程；删除时同时删除内容与元数据。达到保留上限时按创建时间清理最旧条目，并同步清理其元数据。

## 动态结构

`dae export outline` 返回版本、叶子类型、字段映射、数组标记、默认值、必填标记和字段说明。面板直接展示当前二进制返回的结构，不维护固定字段清单。

原始 `.dae` 文本仍是权威数据。动态结构用于发现和浏览能力，而不是将未知文本解析后重新生成，因此上游新增语法不会被旧面板删除。

## 可视化编排

全局设置、DNS、节点、订阅、分组和路由的可视化视图由浏览器端的节级解析器从配置文本派生（`web/src/utils/daeconf.ts`）。该解析器只做两件事：把文本切分成节与条目以供展示，以及对被编辑的那一行或那个子块做定点改写。卡片右上角的“编辑原文”只替换当前节，仍留在代理编排页；不会跳转到全局配置编辑器。

它刻意不是一个完整的 DSL 解析器，因此有三条硬性纪律：

- **不重新生成配置**。未编辑的行、注释、空行和无法识别的节都逐字节保留，包括原有的 CRLF 行尾。
- **拿不准就不改**。当一行包含多个条目、条目跨行、或落在块注释内时，解析器不把它列为可编辑条目；用户可在对应卡片的“编辑原文”中处理整个节。
- **不是安全边界**。编排结果整体经 `PUT /api/v1/config` 写回，仍受 SHA-256 乐观锁、`dae validate`、备份和重载失败回滚保护。解析器出错的最坏情形是 dae 拒绝候选配置，磁盘内容不变。

词法规则以上游 [`dae_config.g4`](https://github.com/daeuniverse/dae-config-dist) 为准：`#` 与 `/* */` 注释仅在 token 边界生效、字符串剥引号时不做反转义、声明的键必须是裸 ID。这些规则由 `web/src/utils/daeconf.test.ts` 锁定。

`global` 表单覆盖 dae 当前公开的全局字段，包括 pprof、eBPF 连接表、透明大页和 TLS 分片等设置。当前二进制是否支持某字段及其默认值由 `dae export outline` 动态确认；不支持的字段会明确标记并禁止新增，outline 不可用时退回 `dae validate` 裁决。省略的字段不会因为打开或保存表单就被批量写入，只有用户实际修改的声明才会定点替换或追加。未知、重复和跨行声明保持原样并锁定对应控件，交由 `global` 原文编辑器处理。

DNS 简单模式覆盖 dae 当前公开的 `dns` 字段：IP 版本偏好、监听地址、乐观缓存、缓存容量、固定域名 TTL、上游以及 request/response 路由；字段支持情况与默认值同样来自当前二进制的 outline。没有 DNS 节时，编辑器提供与 daed 一致的 AliDNS/Google DNS 起始方案，但只有用户点击“应用到编排”才会真正创建配置。包含注释、未知字段、重复块、跨行规则或无法完整往返的内容时默认进入进阶模式。简单表单与进阶原文各自保存独立草稿，标签切换不做解析、生成或写回；取消会丢弃两份草稿，只有当前模式的“应用到编排”会替换 `dns` 节。简单模式重建整节前会明确提示可能移除未知文本，最终仍由 `dae validate` 裁决。

从没有 DNS 编排的旧版升级时，配置管理与代理编排会在浏览器内为缺少 `dns` 节的入口配置生成默认 DNS 草稿并标记为未保存；不会在页面加载时静默改写磁盘，只有用户明确保存后才进入配置事务。恢复缺少 `dns` 的历史备份也遵循同一规则，备份文件本身保持不可变。

路由另外提供两层编辑：常见单行规则可增删改，新增规则总是插到 `fallback` 前；“编辑路由”中的简单模式覆盖整个 `routing` 节，生成 GFW、中国列表以外、仅代理中国列表、全局、全直连或指定 MAC 设备的模板。简单模式只在现有内容能完整往返时才自动选中；含注释、额外规则或未知分组时会直接进入高级模式，避免一次无意的应用丢失用户内容。简单模式和高级模式各自维护独立草稿，切换标签只改变视图，只有点击“应用到编排”才会替换 `routing` 节。最终内容仍经过与其他配置相同的 `dae validate` 和原子保存事务。

## 订阅

订阅的拉取、解析与缓存全部由 dae 完成，面板只维护配置里的那一行文本，不下载订阅内容，也不在本地存节点列表。

因此面板提供的三件事都是围绕 dae 既有行为的：

- **离线缓存开关**：把链接 scheme 在 `https://` 与 `https-file://` 之间切换。带 `-file` 后缀时 dae 会把拉取成功的内容写入 `config_dir/persist.d/<tag>.sub`，并在后续拉取失败时回退使用；这是上游 `example.dae` 记录的能力，不是面板自己的缓存。
- **立即刷新**：运行中按服务后端记录的 PID 执行一次 `dae reload`，dae 借此重新拉取全部订阅；未运行时无需执行。
- **自动刷新**：按间隔重复上一件事。每轮开始前尝试获取全局控制锁，被占用就跳过当轮并记录原因，绝不与用户发起的保存或服务控制交叉。间隔设置持久化为一个 JSON 文件，与面板数据库分开，便于运维直接查看和备份。

分组编辑器可以直接多选带显式标签的本地节点和带标签的订阅，分别写成 dae 原生的 `name(...)` 与 `subtag(...)` 过滤器。批量导入分享链接时，面板会生成唯一的合法标签，并可在同一弹窗中把节点加入已有分组；这使分组引用以配置键为准，不依赖各协议或 dae 版本对链接备注的运行时命名。旧配置可在节点卡片中一键“补全标签”，然后在分组中重新选择这些标签；面板不会擅自把旧 `name(...)` 改成某个本地节点，因为相同名称也可能来自订阅。

daed 能继续展开并逐个选择订阅内包含的节点，那依赖 dae-wing 把节点写进数据库。面板没有常驻数据库存节点，也不去解析订阅内容，因此订阅在分组中以整体选择，不伪造订阅内部节点视图。

## dae 版本管理

默认开启。它只做一件事：把上游的 dae 可执行文件换成你选定的版本。

替换目标以 `dae.service` 的 `ExecStart` 为准，而不是面板配置里的 `KDAE_PANEL_DAE_BINARY`。两者可能不是同一个文件，若替换了后者，事务会全绿而 dae 仍在跑旧二进制——这种静默的假成功比失败更糟，因此以单元为准，并在两者不一致时明确提示。

安装是一个带回滚的事务：下载并比对 sha256 → 在目标同目录暂存（不能用 `/tmp`，面板单元开了 `PrivateTmp`，跨文件系统改名会失败，而且 `/tmp` 常以 `noexec` 挂载）→ 用新二进制自证能运行并接受当前配置 → 把当前版本备份到暂存位 → 原子替换。dae 原本运行时才会重启，并在观察窗口内持续确认 active 且重启计数不再增长；原本未运行时只替换文件并保持未运行。运行中的切换失败会恢复备份并把服务重启回去。观察窗口同时盯两个信号：systemd 的 `NRestarts`，以及主进程号是否发生变化——后者是为 procd 补的（procd 不暴露重启计数器，`Restarts` 恒为空），但对 systemd 同样生效，两个信号任一触发都判定为观察期内发生过崩溃重启。

下载完成的二进制进入 `/var/lib/kdae-panel/dae-versions/` 本地版本库。每个版本是一个原子提交的自描述文件，元数据与二进制不会出现只写了一半的组合；文件名由来源、版本号和本机首选构建共同做 SHA-256 得到，外部版本字符串从不直接参与路径。元数据另行记录上游最终命中的实际构建，后者可能因资产缺失而比首选构建更保守。列表页只读取有长度边界的元数据，切换时才读完整文件、重新计算 SHA-256 并检查 ELF 文件头。校验失败的缓存会被弃用并重新从上游下载。被替换的当前版本也会进入版本库，但前提是磁盘摘要与面板账本一致——摘要漂移的未知文件不会被冒充成某个已知版本。

x86 优化构建按完整的 x86-64-v2/v3 指令集要求选择，而不是看见 `sse4_2` 或 `avx2` 单个标志就升级。虚拟机可能只透传部分 CPUID 特性，缺少任一必需特性都会回退到更保守的构建，避免安装后才以非法指令退出。界面把 CPU 架构、本机首选构建和账本记录的实际安装构建分开显示；旧账本无法确认实际构建时明确显示未知，不拿当前首选值倒推历史事实。

本地版本与上游清单合并展示，因此超出清单范围或已经从 Actions 过期的构建仍可切换；上游离线时也能只靠缓存工作。删除本地版本只移除版本库文件，不碰当前运行文件和事务回滚点。回滚点继续独立保留：它还要承接面板接管前的外部版本，并保证一次失败切换能够立即恢复，不能依赖用户可能随时清理的缓存。

回滚点的含义始终是"磁盘上这一版的前一版"，因此备份先写暂存位，等事务结算时才决定提升还是丢弃：磁盘留下新版本就提升，退回旧版本就丢弃。少了这一步，一次失败的安装会在动手前就把用户真正想回去的那一版覆盖掉。回滚失败与"回滚成功但服务没起来"是两件事，分开上报——合成一个布尔值会让用户误以为一切已恢复原状。

dae 原本运行时必须重启而非无损重载，因为 eBPF 程序要重新挂载。因此运行中的升级会中断现有连接，这一点与配置保存的体验不同；已经停止的 dae 不会被版本切换擅自启动。

卸载同样按事务处理：先确认面板账本与当前二进制摘要一致，并核对 systemd 单元位于标准路径且确实启动该二进制；随后停止并禁用服务，把二进制、单元和版本账本原子移到同目录暂存位，再执行 `daemon-reload`。配置与 geo 默认保留；用户可独立选择删除哪一类，选中的数据会加入同一事务，目录不可写时在停止服务前直接拒绝。任何一步失败都会把文件、开机启动状态和原运行状态恢复。

两个来源的"版本"含义不同，界面分区呈现：官方发布的版本是 tag，可回到任意历史版本；kdae 分支没有发布，列出的是每一次成功的 CI 构建，产物保留 90 天。未缓存的过期构建不可安装，已经下载到本机的版本不受上游保留期影响。

GitHub 匿名 API 只有每个出口 IP 每小时 60 次。所有 JSON 元数据在进程内缓存 10 分钟，相同 URL 的并发请求会合并；上游限流或短暂故障时沿用最近成功结果。用户从列表点击安装时，官方来源复用列表里的 Release 资产信息，kdae 来源复用已经完成的 run 来源核验，避免安装动作立即重复查询。可选 Token 由独立 `0600` 文件或部署环境提供，HTTP 客户端每次请求动态读取，因此在设置页保存后无需重启；Authorization 只加到 `api.github.com` 首跳，重定向回调再次强制剥离，下载站与 dae 子进程都拿不到它。

机器上还没有 dae 时走首次安装：除可执行文件外，还写入 geo 数据、种子配置与 systemd 单元，然后 `daemon-reload`。服务单元、geo 与可执行文件取自同一个发布包并由同一个 sha256 覆盖；种子配置编译在面板自身中，因而不需要引入新的下载源或信任根。面板不再采用上游 `empty.dae`，因为它缺少面板默认提供的 DNS 编排。

geo 数据写进配置文件所在目录。dae 查找它们时，配置目录的优先级高于所有系统目录（仅次于 `DAE_LOCATION_ASSET`），而该目录本来就在面板的 `ReadWritePaths` 里——这样既不必放宽沙箱，也不必另找下载源。

## geo 数据更新

Geo 管理是侧栏一级入口，由 `EnableGeoUpdate` 控制是否启用（默认开启；OpenWrt 上映射到 UCI 的 `enable_geo_update`），与 dae 版本管理相互独立。关闭时面板不构造 Geo 管理器，`registerGeoRoutes` 把六个 geo 端点全部接成 `503 geo_update_disabled`，侧栏页面据此提示而不是崩溃。启用时更新只写一个数据目录，不碰可执行文件也不碰服务单元。

升级 dae 的事务只替换二进制，从不触碰 geo；首次安装写入的那份也永远不会被自动更新。因此没有这个功能时，geo 会一直停在装上的那一刻。

两个内置来源都来自 GitHub Release，两个文件各自比对随发布的 `.sha256sum`：

| 来源 | 仓库 | 说明 |
|---|---|---|
| `loyalsoldier` | `Loyalsoldier/v2ray-rules-dat` | 中文社区常用的重编排规则集，每天发布；分类更细 |
| `v2fly` | `v2fly/geoip` + `v2fly/domain-list-community` | 与 dae 发布包同源；`geosite.dat` 在上游名为 `dlc.dat` |

来源模型是"每个文件各有出处"而不是"一个来源一个仓库"：v2fly 把两个文件放在两个仓库里，各自独立发布、tag 也不同。因此展示用的版本标识在两文件同属一次发布时直接用那个 tag，来自不同仓库时如实分别列出（`geoip 202607171233 / geosite 20260726062913`），不编造一个看起来统一、实则不存在的版本号。

**两个来源的规则集不是同一套。** 切换后 `geosite:` 规则匹配的域名集合会变，而 dae 照样 validate 通过、照样运行——属于静默的行为变更。界面只在**切换来源时**警告，沿用同一来源只是把数据往前推，每次都弹同样的警告反而会稀释真正的风险。账本记下每次用的是哪个来源，下次默认预选它。

管理员还可以保存多组自定义来源，每组由两个数据直链和两个 SHA-256 校验直链组成，原子写入独立的 `0600` JSON 文件。自定义客户端不携带 GitHub Token；保存时限制公网 HTTPS 语法，下载首跳与每次重定向重新解析 DNS，连接前再由 `Dialer.Control` 检查实际地址，抵御内网访问与 DNS 重绑定。数据和校验文件都有硬体积上限。当前账本使用的来源禁止删除，避免定时任务静默换成另一套规则集。

写入位置不是写死的，而是两个当前有效文件所在目录中搜索优先级最高的那一个：按 `DAE_LOCATION_ASSET` → 配置目录 → `/root/.local/share/dae` → `/usr/local/share/dae` → `/usr/share/dae` 的顺序选择。两个文件都不存在时才退回配置目录。不能按文件名顺序随便挑一个目录，否则 geoip 与 geosite 分居两处时会把更新写进低优先级目录，留下悄无声息的混合版本。被遮蔽的副本会在界面上列出来。

更新是一个可回滚的事务：校验输入恰好包含两份非空数据 → 沿完整搜索路径放回上次中断留下的回滚点 → 重新选择目标目录 → 暂存 → 旧文件改名留作回滚点 → 原子替换 → 重新 locate 并确认两个文件都从目标目录生效 → 运行中的 dae 按服务后端记录的 PID（systemd 的 `MainPID`、procd 的实例 PID）执行 `dae reload`。恢复必须排在选目标之前：中断留下的正式文件是缺失的，只看当前有效文件会退回配置目录，从此再也扫不到低优先级目录里的回滚点。服务状态查询失败时拒绝落盘，查询不缓存，故障解除后可直接重试。理由分后端，提示措辞也分后端：systemd 丢的是单元里声明的 `DAE_LOCATION_ASSET`，它可以指向任意目录，读不到就会把更新写进优先级更低的地方而永不生效；procd 上这条不成立——`dae.init` 与面板 `config_load` 同一份 UCI，`DAE_LOCATION_ASSET` 恒等于 `dirname(dae_config)`，即搜索顺序里本来就有的那一项，读不到它搜索路径一个字都不差，丢的是实例 PID，状态未知会退回不带 PID 的 `dae reload`，先搬几十兆再在重载上失败然后整个回滚。

崩溃恢复只认一种线索——`*.kdae-panel-previous`。要恢复的只有一种状态：进程死在"旧文件已改名、新文件还没换入"之间，此时正式文件根本不存在，dae 一重启就会因为读不到 geo 而起不来。reload 之后没删干净的回滚点长得一模一样，也会被同一条路径放回去，那只让 dae 短暂退回上一版规则集，紧接着的这次更新马上覆盖它。刻意不为区分这两者引入持久化的提交标记：geo 随时可以从上游重新下载并自校验，一套 marker 协议买到的东西远配不上它的复杂度。既存回滚点绝不被下一次事务覆盖——真撞上就说明恢复没生效，覆盖它等于删掉仅存的旧数据；异常目录阻塞恢复时保留回滚点并给出准确路径，修正后可以重试。reload 成功后删除回滚点，删不掉不影响本次结果，只作为告警报出来。dae 未运行时跳过 reload，新文件在下次启动时读取。两个文件同进同退——只换掉其中一个会让 dae 拿着两个版本的规则集跑，而这种不一致既不报错也无从察觉。

运行中的 dae 只需 reload 不需 restart：面板使用服务后端记录的 PID（systemd 下是 `MainPID`，procd 下是 ubus 返回的实例 PID），不依赖可能缺失的默认 PID 文件；reload 会重建控制平面并重新编译路由规则，从而重读 geo。dae 的切换预算约 10 秒，进行中的长连接仍可能被中断，界面据实描述而不宣称"完全无感"。服务未运行时不执行无意义的 reload，也不把“缺少 PID 文件”误判为 Geo 更新失败。

`dae validate` 不加载 Geo 数据，因此分类是否存在只能在真正启动或 reload 时发现。Geo 更新会直接检查 reload 输出，服务控制和版本切换失败后还会读取操作开始以来的近期服务日志（systemd 下是 journald，procd 下是 `logread`）；两条路径都识别 `not found in geoip.dat/geosite.dat`，把分类名、Geo 页面处理入口以及“修改二进制无效”写进错误，版本事务仍照常恢复原二进制。

**首次安装完成后不会自动启动 dae。** 它是透明代理，在一台你正通过 SSH 或反向代理访问的机器上，配置不当地启动会切断你自己的连接。面板种子配置内置 AliDNS/Google DNS 起始方案，但不声明任何网卡，因而不会接管透明代理流量；写好真正的规则之后，由你在服务控制页显式启动。

面板不覆盖已存在的配置，也不覆盖已存在的 geo 数据——用户可能自己维护着一份裁剪过或更新更勤的版本。已存在的服务单元同样不覆盖，两个例外：它与本次将写入的内容逐字节相同（上一轮安装留下的；少了这个例外，`daemon-reload` 失败后的重试会被自己写下的单元永久挡住），或者它的 `ExecStart` 已经指向面板要装的那个文件（官方安装器写的、用户自己调过的单元都算——它能把新装的二进制起起来，就没有理由为了统一格式去覆盖别人的文件）。

单元冲突在动任何文件之前就查出来。放到最后才查的话，二进制早已换掉而报出来的错只谈单元，留下一台装了一半、错误信息还答非所问的机器。

还有两种局面容易被忽略，都单独处理了：目标位置已经躺着一个 dae 但 systemd 里查不到它（先备份再替换，不是直接覆盖）；单元在而它启动的文件不见了（升级说"目标不存在"、首次安装说"已有服务"，两条路都走不通，面板反而修不好自己造成的局面——现在按单元指向的位置补齐）。

## 当前观测边界

在不修改 dae 的前提下，面板可以可靠获得：

- 服务运行状态、PID、内存、本次运行时长、任务数和开机启动策略（systemd 与 procd 都拿得到；
  只有重启计数是 systemd 独有的，见「服务后端」）；
- 服务日志（systemd 下是 journald，procd 下是 `logread`）；
- dae 版本、命令能力和配置结构；
- sysdump gzip 诊断归档（在私有临时目录生成，读取后立即清理）；
- 面板主机到节点服务器的 TCP 握手延迟（`POST /api/v1/net/latency`）。

延迟探测由面板自己发起，衡量的是面板主机到 `host:port` 的 TCP 可达性，与 dae 依据 `tcp_check_url`/`udp_check_dns` 得出的健康状态是两码事：它不做协议握手，域名目标还包含名称解析时间，也不代表 dae 选路时看到的延迟。此外 dae 配置 `wan_interface` 时会劫持本机进程流量，面板的探测连接也会按 dae 的路由规则转发，未必是物理直连。界面按“直连延迟”呈现并在提示中说明这些前提，不冒充 dae 的健康检查结果。

探测目标由管理员的配置决定，可能合法指向内网或回环地址，因此不做地址段过滤；约束来自端点的认证与 CSRF 校验，以及面板进程级的并发上限（16 个并发拨号，跨请求共享）。

以下数据没有稳定公开接口，当前不伪造或解析内部实现：

- 实时连接列表与 UDP 会话数；
- 每条路由的命中统计；
- dae 维度的精确流量与实时速率；
- 内部 DNS 缓存；
- 每个出站节点的真实运行时健康状态，以及 `min_*` 策略当前选中的节点。

上游把这些数据放在进程内 Go API（`control.SnapshotRuntimeStats`、节点延迟探测）里，明确供 dae-wing 一类进程内消费者使用，没有对外的 socket 或 HTTP 端点。面板与 dae 分离运行，因此不去猜测这些数值。未来若 dae 提供稳定的只读接口，可以作为可选适配器接入，不影响现有 CLI 路径——届时先扩展能力探测与上游契约测试，再启用对应界面。

## 上游契约验证

定时 CI 会构建 `olicesx/dae` 的 `kdae` 分支，并使用真实二进制执行 `--version`、`--help`、`export outline`、`validate -c` 和 `sysdump`。`reload`、`suspend` 只验证命令能力，不在 CI 主机发送进程控制信号。这一项每周跑一次。

版本发现契约是另一个独立的 job，每天跑一次：它对真实上游列出版本、解析资产、下载并解包，断言取出的确实是 ELF。它刻意不挂在构建 kdae 之后——上游一旦构建坏掉，这个检查就完全不跑，而它恰恰是唯一能发现"上游改了打包方式，面板一个版本都装不上"的地方。这类问题此前真的发生过：官方发布包里的可执行文件叫 `dae-linux-x86_64` 而不是 `dae`。

两项都不在 PR 上跑：它们验证的是上游而不是这次改动，让 PR 依赖第三方可用性与匿名 API 限额并不划算。
